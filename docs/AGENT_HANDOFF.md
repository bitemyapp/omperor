# Omperor Agent Hand-off

_Status date: 2026-09-10. Repository baseline: Omperor `main` at the rebase commit that follows `d9c9506` (see the commit map); vendored oh-my-pi branch `codex/omperor-rpc-reliability-omp2` at `248847efb8`, twelve commits on top of upstream `omp2` `2f92f3b5aa`, on the OMP fork that the submodule anchors on._

## Purpose and direction

Omperor is an experimental native macOS desktop agent application built almost entirely in Rust. The product goal is a fast, polished, Mac-native alternative to a browser-based chat shell that reuses oh-my-pi (OMP) as its inference and agent harness instead of reimplementing provider authentication, model protocols, session execution, tool orchestration, and transcript persistence.

The native requirement is deliberate: the interface is built directly against AppKit through `objc2` and `objc2-app-kit`, uses TextKit for text layout, and does not embed WebKit or another browser engine. There is currently no Swift or Objective-C façade. Unsafe code is limited to the Objective-C message and framework boundaries required by the Rust bindings, and the crate enables `#![deny(unsafe_op_in_unsafe_fn)]`.

The current implementation runs OMP as one managed release-build child process and communicates with it through the typed `omp-rpc` crate. This is not the originally preferred in-process sans-I/O architecture, but reliability patches, bounded startup, automatic recovery, and graceful shutdown have made the child-process design workable. Moving OMP in-process remains a possible longer-term direction, but should only be attempted with a clear library boundary and a smaller blast radius than copying its agent logic into Omperor.

The next major product discussion is projects. Omperor currently has one active workspace path persisted as a preference; it does not yet have a first-class project registry, project-specific settings, multiple simultaneous project contexts, or explicit worktree lifecycle management.

## What the product can do now

- Open quickly into a native three-pane workspace: session navigation on the left, rich chat in the center, and Git environment/status inspection on the right.
- Start new OMP-backed agent sessions, submit prompts before OMP has finished starting, stream responses, steer an active turn, and stop a running turn.
- Paste clipboard images into the message field or drop files onto the composer or conversation. Pending attachments show preparation/errors and a Remove action; attachment-only messages are supported. Up to 16 attachments may be pending. Switching conversations clears pending attachments. Observatory hides attachment chips and rejects attachment ingress; returning to Conversation restores pending chips. Attachment messages wait until an active turn finishes, because OMP steering accepts text only.
- Native Edit-menu key-equivalent dispatch refreshes Paste validation before routing Command-V. AppKit can otherwise retain a stale text-only target when the composer loses its field editor after RPC stops: opening Edit would attach an image while the keyboard shortcut silently did nothing. Clipboard images can be prepared while RPC is unavailable; sending still requires a connected session.
- Attachment preparation (file reads, MIME sniffing, TIFF-to-PNG conversion, base64 and prompt assembly) runs on the worker pool with an activity indicator. Supported images up to 8 MiB become RPC image parts; TIFF sources have a separate 64 MiB limit and are converted before applying the 8 MiB PNG output limit. Image size and TIFF conversion failures remain explicit failed attachments, never silently downgraded to file paths. UTF-8 text up to 128 KiB is included as quoted text. Other file types and larger non-image files are delivered as explicit absolute-path references for OMP tools, not misrepresented as inline model content. Clipboard snapshots are private files retained under Omperor's `omp/data/attachments` directory so later tool reads remain possible.
- Show reasoning/thinking updates and detailed tool activity rather than hiding the agent's work.
- Expose OMP's standard GUI-safe tool set: `ast_edit`, `ast_grep`, `bash`, `debug`, `edit`, `fetch`, `glob`, `grep`, `lsp`, `read`, `think`, `todo`, and `write`.
- Authenticate OpenAI and Anthropic subscriptions through OMP's existing authentication flows, open browser login URLs, accept callback values when needed, and visibly return an expired account to a reconnect state.
- Discover models from the authenticated OMP runtime instead of presenting a global catalog full of irrelevant or synthetic models.
- Change model and reasoning effort, with model changes confirmed by OMP before the GUI updates its selected state.
- Persist Omperor-native sessions in an isolated directory and resume those sessions after restarting the app.
- Browse foreign OMP/TUI sessions separately and explicitly as read-only, without attempting to attach a competing writer.
- Load Omperor sessions before external OMP sessions, load the newest tail of a transcript first, and prepend older pages without moving the user's viewport.
- Render native Markdown including headings, emphasis, strikethrough, inline code, links, lists, task lists, blockquotes, tables, fenced code, syntax highlighting, diffs, and local or remote images.
- Preserve user scroll control during streaming: new output follows only while the viewport is already near the bottom.
- Inspect the active Git workspace, list changes, and render selected diffs with language-aware syntax highlighting plus diff-line coloring.
- Configure workspace, model, reasoning, appearance, transcript text size, inline images, storage visibility, and accounts from a native Settings window.
- Hold several accounts per provider in OMP's store, list them on the Settings Accounts page with a user label, the subscriber email or authentication time, a per-provider default, and rename/remove actions.
- Pin one account per provider for the running session, show it in the composer beside the model and reasoning controls, remember the choice per project, and ask the user to choose when a provider has several accounts and nothing decides.
- Group sessions under projects in the sidebar, with a per-project "+" for a new chat, collapsible headings, a "New project…" folder chooser, and a Settings Projects page for renaming, adding and removing folders, and deleting projects.
- Fork any Omperor session from its row's context menu (right-click, or the "…" button that appears on hover): "Fork Session" starts a fresh session seeded with the transcript in the same folder, and "Fork into New Worktree…" also creates a git branch and worktree from the commit that folder has checked out. Forks are filed under the same project without nesting; lineage lives in the record and tooltip.

## Work chronology

### Phase 1: Native shell and session viewing, 2026-08-30

The first work vendored the `omp2` branch as a Git submodule at `vendor/oh-my-pi` (`f528400`) and scaffolded a native chat-window demo (`fb18064`). The initial success criterion was deliberately small: prove that a Rust application using native macOS controls could feel fast and be built without opening the Xcode GUI.

Read-only OMP session discovery and history rendering followed (`f6655e7`), then the history browser was separated from the live chat surface (`1c45d44`). This established the principle that existing TUI sessions should be inspectable without assuming they are safe to resume.

### Phase 2: Live OMP integration and tools, 2026-08-30 through 2026-08-31

The Chat view was connected to OMP RPC (`c8b5985`). Authentication and inference lifecycle problems were fixed (`ab045a0`), followed by OpenAI Codex transcript compatibility for multi-turn replay (`e8af369`). OMP's standard tools were then enabled (`397171c`), the eval routing bug was repaired (`effadc7`), and reasoning/tool arguments, updates, results, and failures were projected into the native conversation (`50729ba`).

This period exposed several protocol mismatches: assistant history had been replayed as `input_text`, strict tool schemas were not accepted by the Codex route, and speculative tool arguments could fail to relay. The local OpenAI compatibility patch in `patches/oh-my-pi/0001-force-codex-http.patch` contains the remaining build-time transformations needed by the bundled helper.

OMP startup was moved off the main thread and app shutdown began waiting for the child (`cb10809`). A shutdown race still caused hangs when quitting during startup, so termination was made asynchronous and race-safe and a lifecycle stress script was added (`9aa2744`).

### Phase 3: Workspace control plane and native rich rendering, 2026-08-31 through 2026-09-01

The application grew from a demo into a native workspace shell (`09231c5`): persisted preferences, workspace selection, Git status/diff inspection, model and reasoning controls, session navigation, and agent controls were added. Live steering arrived in `ddd6062`, and the visual structure was rebuilt as the current three-pane AppKit interface in `b17dc54`.

Native rich chat rendering was implemented in `9c037b3`. The first renderer exposed layout problems in code blocks, missing tables and images, unstable scrolling during streaming, and Enter-key submission gaps. The resulting implementation uses a structural Markdown parser plus native attributed text, TextKit tables and attachments, a cached syntax set/theme, controlled code baseline spacing, asynchronous image loading, and viewport anchoring. The work was visually iterated after macOS Screen Recording permission was granted; future GUI changes should continue to be tested visually rather than inferred from a successful build.

The same rendering pipeline was extended to the environment sidebar so selected Git diffs receive syntax highlighting and added/deleted/hunk treatment instead of appearing as an unstyled monospaced dump.

### Phase 4: Instrumentation, startup, RPC reliability, and durable sessions, 2026-09-01 through 2026-09-02

Internal GUI spans and every material OMP boundary were instrumented in `9197783`. Controlled debug-versus-release runs proved that native window presentation was about 0.2 seconds in both profiles while OMP RPC startup was approximately 13.0 seconds in debug and 4.3 seconds in release. Omperor therefore always uses a release OMP helper, even when Omperor itself is built in debug mode.

Further profiling showed that a cold OMP helper is unusually expensive because its approximately 278 MB Mach-O contains roughly 267 MB of executable/read-only content and tens of thousands of signed pages. A no-op Cargo build changed filesystem metadata and invalidated warm executable validation despite identical bytes. The build scripts now install OMP at a stable path, hash all meaningful build inputs, skip unchanged release builds, and avoid replacing the installed helper when its bytes have not changed. Warm RPC readiness was measured around 0.9–1.0 seconds; the first cold launch remained around 4.6 seconds.

Startup interaction was redesigned so the native window appears first, New Chat can be accepted during the OMP handshake, and one initial prompt can be queued and dispatched after readiness without killing and respawning the backend. OMP startup is bounded to 15 seconds (`0b8343c`) and failed/disconnected instances enter recovery rather than leaving the UI indefinitely stuck at “waiting for OMP.”

OpenAI authorization expiry now produces a provider-specific reconnect state (`28a22f8`). Queued chats survive OMP restarts (`36e4ec7`). Session history loading was changed to reverse, incremental pages (`184e0f2`) so the newest state renders first while older history arrives in the background.

Repeated “third new chat hangs” and “child exited before ready” failures led to direct work in the OMP fork. Transport disconnects are propagated, environment hello handshakes are bounded, idle session-actor model changes are processed, and graceful RPC teardown is fixed. These changes are on the public fork branch and are listed in the OMP fork section below.

Omperor-native sessions and OMP backend state were isolated under the app's Application Support directory and resumability was added in `86e050a`. Source tabs were added in `6726c9e`: the default `Omperor` tab contains app-owned resumable sessions, and `OMP · Read-only` contains foreign TUI sessions. The earlier idea of cloning/forking a foreign OMP session into Omperor was not implemented; keeping external sessions read-only was the safest solution without adding ownership/locking semantics to OMP.

### Phase 5: Settings, accounts, and model truth, 2026-09-02

The most recent Omperor commit, `0307aa0`, added a substantial native Settings window with General, Agent, Appearance, Sessions & Data, and Account sections. It also added Anthropic subscription authentication and made model choices account-aware.

An early model picker accidentally surfaced OMP's enormous cross-provider discovery catalog, including models that were irrelevant to the connected subscription and placeholder-looking entries. The current picker is restricted to supported models advertised for authenticated OpenAI/Codex and Anthropic providers.

Anthropic discovery initially exposed selector annotations such as `[1m]` as though they were part of the provider's wire model ID, and inference still identified its Claude client as version `2.1.220` even though Fable 5.1 requires at least `2.1.251`. OMP now normalizes selector annotations, invalidates stale cached rows, confirms model changes transactionally, and consistently identifies as Claude Code `2.1.258`. An authenticated direct-inference test and a raw RPC test both returned successfully with a journal receipt naming `anthropic/claude-fable-5-1`.

### Phase 6: Multiple accounts per provider with explicit selection, 2026-09-03

The user decided that multi-account support should be explicit selection only; automatic rotation and pooling across subscriptions were deferred because they need more design. Investigation showed OMP already stores several accounts per provider (`account_id` is `provider:principal`, where Anthropic's principal is the subscriber email and OpenAI Codex's is an opaque workspace identifier) and already selects among them by quota through `crates/inference/src/account/pool.rs`, but its RPC surface exposed only one boolean per provider and its journal "credential pin" slot is written and never consumed at inference time.

The fork commit `b42a110a61` adds a host-owned, per-provider principal pin. `AccountPins` in `crates/inference/src/call.rs` is shared between the RPC runtime and the session's inference facade; `Client::plan` attaches a snapshot to every call and `RouteAccountSelector` in `crates/inference/src/provider/builtin.rs` prefers the pinned principal over provider-state affinity, so a pin that disagrees with an existing server-side binding reseeds through the existing session-expiry path. The RPC gains `list_accounts`, `set_account { accountId }`, and `logout_account { accountId }`, reports pins in `get_state.accountPins` and `config_update`, and re-derives each provider's `authenticated` flag from the live account list. OMP's account listing does not carry labels, so labels live in Omperor.

Omperor's side is uncommitted in the working tree. `src/preferences.rs` gained a versioned migration mechanism (`PRAGMA user_version`, currently 1) and two tables: `accounts(account_id, provider, principal, label, authenticated_at_ms, is_default)` and `project_accounts(project, provider, account_id, chosen_at_ms)`. `src/omp_runtime.rs` lists accounts at startup, pins the launch configuration's account before Ready, and adds `SetAccount`, `LogoutAccount`, and an account on `NewSessionWithModel`, with `AccountChanged` and `AccountsChanged` events. `src/main.rs` rebuilds the Settings Accounts page dynamically inside a scroll view, adds a transparent account popup beside the model and reasoning pickers, resolves the account for the active provider as workspace memory, then the session's pin, then the only usable account, then the provider default, and otherwise blocks sending until the user chooses. Labelling is obligatory once a provider holds two or more accounts: an app-modal prompt names every unlabeled account and refuses empty or duplicate labels. Renaming, setting a default, removing (through OMP's real logout), and choosing an account when switching a model to a provider with several accounts are all modal `NSAlert` flows guarded against re-entrancy from the runtime poll timer.

Verification on 2026-09-03: OMP `check`, `fmt-check-rust`, and clippy (repository invocation) passed for the touched crates; Omperor `cargo fmt --check` and 82 tests pass; the debug app with the rebuilt release helper was launched twice, the Accounts page, rename prompt, default radio, composer account control, and sidebar footer were inspected from screenshots, and a real Anthropic turn completed under the pinned account with the second launch pinning before Ready. What was not verified visually is the two-accounts-per-provider path itself (label prompt, account popup with several entries, choose-account modal, removal): the only way to stage a second account without a second real subscription is to write a copied row into OMP's encrypted credential store, and this session's automation policy blocked writing to that store. Staging such a row by hand, with SQL against `<data dir>/omp/data/credentials.db` while Omperor is closed, is safe (the script used at the time held real account data and is no longer in the repository); OMP's encryption binds account identity as associated data, so the staged account lists and pins but can never serve inference, and Settings → Accounts → Remove… deletes it again through OMP's real logout.

### Phase 7: Projects as folders of sessions, with worktree forks, 2026-09-04

The user chose the Codex and Claude Code shape for projects: a project is a folder of sessions, and every session is bound to exactly one directory, either one of the project's folders or a git worktree Omperor created when the session was forked. The alternative, one working directory plus additional authorized roots through OMP's `--add-dir`, was rejected for now because it merges instruction files from every root and widens write access; the chosen shape can grow into it later, whereas the reverse would mean redoing the launch model. The Git inspector follows the active session's directory only, existing sessions were auto-filed into one project per distinct directory on first launch, and "Project" replaces "Workspace" throughout the interface.

Storage moved to schema 2 in `src/preferences.rs`: `projects`, `project_directories` (a directory belongs to at most one project), and `sessions` (Omperor's record of a session's project, directory, parent, branch, base branch, and worktree path). `project_accounts` keeps its shape but is keyed by project id; the bootstrap adopts rows that were keyed by directory path. The bootstrap runs once, after the first Omperor session discovery, and records a `projects_bootstrapped` flag in the key/value table.

The runtime gained `ForkSession { session_id, project }`, which relaunches the child with `--fork <id> --fork-moved` in the worktree; once the child reports Ready the launch configuration converts the consumed fork into a resume target so recovery never forks the parent twice. `src/workspace.rs` gained `branch_point`, `is_valid_branch_name`, and `add_worktree`, which runs `git worktree add -b <branch> <path> HEAD` under `~/Library/Application Support/Omperor/worktrees/<project id>/<branch slug>`. The fork commit `5da5323b76` adds `SessionOpen::ForkMoved` next to `ResumeMoved`, because OMP otherwise refuses to fork a session whose canonical project differs from the working directory, which is exactly what a fresh worktree is.

In `src/main.rs` the sidebar rows are computed by the pure function `sidebar_rows_for`: project headings in the user's chosen order, members in discovery order without nesting (the user rejected structural nesting of forks; two sessions may work on orthogonal parts of one checkout), an "Other folders" heading for Omperor sessions no project owns, and the flat read-only OMP list on the other tab; a search ignores collapse state and hides projects without a match.

Typing `@` in the composer opens a file-reference picker. Its logic is `src/file_picker.rs`, pure Rust with no AppKit so it runs on the worker pool and is unit-tested on its own (branch `experiment/fff-picker-benchmark` benchmarks it against the `fff-search` crate; `docs/FFF_PICKER_BENCHMARK.md` there records why fff was not adopted). `index_project_files` lists the active project's files with the `ignore` crate's walker (the one `fd`/ripgrep use): it honors `.gitignore` but descends into every subdirectory — including git submodules and nested repositories, which `git ls-files` reports only as a gitlink, so it missed the ~11k files vendored under `big-bang-astra`'s submodules. Each `ProjectFile` carries its modification time and depth, and the index is sorted once, off-thread, into browse order — most recently modified first, then shallowest, then by path — so a bare `@` simply shows the index's first rows: what was just edited, or on a fresh checkout a root listing. The index is held as an `Arc`, refreshed alongside the Git inspection when the project changes, and capped only to bound memory on a pathological tree. `controlTextDidChange:` finds the active `@token` at the caret (`active_at_query`) and submits `filter_project_files` (basename prefix, then substring, then subsequence) to the worker pool — scanning 30k paths takes ~4 ms, too long for the main thread — tagged with a generation counter; a `FilePickerFiltered` result whose generation is stale (a later keystroke, Escape, a commit, or a send bumped it in `hide_file_picker`) is dropped, and an `@token` typed before the index exists is answered when `ProjectFilesIndexed` lands unless the picker was dismissed meanwhile. The results render in an in-window overlay box above the composer — not a child window, so the field keeps focus and `control:textView:doCommandBySelector:` drives it: arrows move the highlight, Return or Tab inserts the path (replacing the `@token` in the live field editor), Escape dismisses. Rows refuse first responder so a click completes without ending the editing session. Only files are offered.

The file index and the Environment pane refresh on the same triggers. `refresh_project_files` runs unconditionally at the top of every `start_workspace_inspection` — so after each file-changing tool (`tool_may_change_files` → `request_workspace_refresh`), the Refresh button, a project switch or relocation, and a vanished change — coalesced by two flags: a request while a walk is in flight queues exactly one more, run when `ProjectFilesIndexed` lands; a keystroke in the picker only calls `ensure_project_files`, which walks solely when nothing is indexed for the current directory. Changes made outside Omperor are caught by `src/file_watcher.rs`: an FSEvents stream on the project root (`kFSEventStreamCreateFlagFileEvents`, 0.5 s latency) scheduled on a dedicated thread's run loop, whose callback filters events on that thread and sends the root through a channel the 30 Hz poll timer drains. The filter (`ChangeFilter`) applies git's own rules: `.git/index` and `.git/index.lock` — of the project or of a nested repository under `.git/modules/` — never count, since every `git status` including the inspection's own rewrites them (the rest of `.git` does, so a commit or checkout in a terminal updates the branch and change list); otherwise the global excludes, `.git/info/exclude`, and every `.gitignore` the index walk honored decide, each scoped to its own directory with the deepest applicable file having the last word, so `sub/.gitignore`'s `*.log` hides `sub/x.log` but not `x.log`, and its `!keep.tmp` overrides a root `*.tmp`. The walk reports those directories in `ProjectIndex::ignore_dirs` (it probes each directory it enters for a `.gitignore`, so a file under an ignored tree is never consulted), the job builds the filter off-thread, and `ProjectFilesIndexed` installs it with `set_filter` — which also means editing a `.gitignore` refreshes the rules, since that edit is itself a relevant change. Two mechanisms keep refreshes from piling up: `poll_project_watcher` records when the tree last changed and calls `request_workspace_refresh` once it has been quiet for `WATCH_QUIET_PERIOD` (1 s), so a build's burst costs one refresh at its end; and every `start_workspace_inspection` stamps the watcher with `FSEventsGetCurrentEventId()` (`mark_covered_through`), so events for changes made before an inspection started — a tool's edits, already inspected at tool end — are dropped when they arrive half a second later instead of prompting a second inspection, while a change made after the stamp still counts. The watcher is swapped whenever the project changes (the old thread sees its stop flag within half a second and tears its stream down itself; nothing on the main thread joins it). If the stream cannot be created the failure is recorded as the `gui.watcher.unavailable` perf event and the inspection triggers alone remain; the `gui.workspace.inspect.requested` perf event (one per `start_workspace_inspection`, carrying the caller's file:line via `#[track_caller]`) and `gui.watcher.refresh` count inspections and watcher-prompted ones — distinct from the `gui.workspace.inspect` span, whose start and end records would otherwise triple the count.

The visual language lives in `src/theme.rs` and is drawn from the crowned-gate mark: gold (`theme::accent`, with `accent_fill` and `accent_wash` at fill and wash strength) for the crown — the active project, the open session's pill, the user's turn in the transcript, the send button — and plum (`plum_wash`, `plum_wash_light`) washed over the sidebar and inspector vibrancy so the side panes read as part of one thing; `surface`, `surface_inset`, `popover`, and `hairline` carry cards, chips, the floating `@` picker (opaque, since it sits over the transcript), and rules. Every color is an appearance-following dynamic `NSColor` built with `colorWithName:dynamicProvider:` (hence the `block2` dependency and the `NSColorList`/`block2` app-kit features), tuned separately for Aqua and Dark Aqua — deep gold on white, light gold on dark — so the app switches appearance without any view being re-tinted; to check the light palette without touching System Settings, launch with `defaults write com.bitemyapp.omperor NSRequiresAquaSystemAppearance -bool yes` and delete the key afterwards. `theme::display_font` is the serif system design (New York) used for the wordmark beside the app icon, the session title, the pane and sheet titles, and the settings page headers; body text stays in San Francisco. `theme::symbol` builds tinted SF Symbols, which the transcript uses as inline attachments for tool status (a filled check, a filled cross, a dotted ring), the row chevron, the thinking spark, and notice marks. In `main.rs`, `fill_box`, `card_box`, `attributed`, `section_label` (uppercase, tracked), `status_attributed` (a colored dot reading the status — green for Ready, amber while something ends in an ellipsis, red on failure words), `key_value_attributed` (the inspector's "BRANCH main" lines), `project_row_title`, and `fit_chip` (the composer's model/reasoning/account chips hug their labels; `refit_composer_chips` re-lays them out after any label changes) are the shared pieces. The activity detail is a sheet (`present_activity_detail` / `closeActivityDetail:`, kept in `activity_sheet`) rather than an `NSAlert`, so the rest of the app stays responsive while it is open; Return and Escape both close it. In the transcript, a user message is enclosed in one `NSTextBlock` shared by all of its paragraphs (gold wash, 3-point gold rule on the left) with any code block, quotation, or table nested inside it, and author labels are small tracked uppercase.

The transcript's typesetting is governed by `native_markdown::Typography`, built from the `Chat style` preference (`theme::ChatStyle`, stored under the `chat_style` key beside `chat_text_size`, chosen on the Settings → Appearance card) and the text-size scale: `Modern` sets the conversation in San Francisco, `Editorial` in New York with a book's measure and a hyphenated rag (`hyphenationFactor` 0.9 on body paragraphs), `Terminal` in SF Mono throughout, labels and tool rows included (`Typography::ui_font`). Each style fixes the body size, the code size (a point and a half smaller than prose, since mono runs wide), the leading, the paragraph spacing, a heading scale, and a measure — the line length in points (680 / 600 / 720 at scale 1) — which `sync_transcript_measure` applies to the text container (`widthTracksTextView` off) and re-applies from an `NSViewFrameDidChangeNotification` on the scroll view's clip view, so the column narrows with the pane but never widens past what an eye returns from comfortably; `refresh_chat_transcript` also caps image widths at it. Space before a paragraph is decided in `render_document` from what precedes it — a heading claims its own air, prose after a table gets a paragraph's worth back (cells carry no paragraph spacing, which is why prose once sat flush under a table's rule), and prose after a quotation likewise. Tables are set as a well-set table is: horizontal rules only — a firmer pair around the header row, a hairline between body rows — no vertical rules and no header fill, and the first column starts on the text edge. A quotation carries no glyph in the text any more (the parser no longer inserts `▎`); `quotation_block` draws a rule down its left edge, consecutive quoted paragraphs abut so the rule runs unbroken, and nesting indents only beyond the first level. A horizontal rule is `rule_block`, a hairline along the paragraph's bottom edge, with the rule's own text set invisibly small so plain copies still carry a separator. A fenced block's language label shares the code's block but gets a 13-point line of its own rather than the code's baseline grid. Headings are semibold (not a bold trait) in the body family, large sans headings tightened by 0.3 points. `examples/markdown_snapshot.rs` renders a rich sample to PDF — `markdown_snapshot <out.pdf> [dark|light] [modern|editorial|terminal]` — set at the style's measure, which is the quickest way to review typesetting changes across styles and appearances; it converts `find` byte offsets to UTF-16 before building ranges, since the sample's bullets precede the code it measures.

Sessions within a project reorder the same way: each session row is a `SidebarSessionButton` whose left-click opens the session and whose vertical drag reorders it within its project (right-click still opens the context menu; the hover "…" button is a separate view). A drag persists positions through `set_session_order` into a `session_positions` table keyed by session id — keyed by id, not a full record, because a session filed under a project by its working directory alone has no record row. `sidebar_rows_for` sorts a project's sessions so any the user has ordered hold their positions while the rest keep floating to the top by recency, so new chats still appear on top and a used session no longer reshuffles once its project has been arranged. Only the sessions under a project are draggable; the flat read-only OMP list and unfiled sessions are not.

Project order is stable by design: it never reorders on its own, only when the user drags a project header. The `projects` table carries an explicit `position` column (migration 3, seeded from the prior last-opened recency order so the first launch looks unchanged); `load_projects` orders by it, `create_project` appends, and `set_project_order` rewrites positions after a drag. Opening a session still records the project as opened but no longer moves it — the earlier move-to-front in `activate_project` was the source of the sidebar reshuffling on click. The fork commit `248847efb8` makes account failures explain themselves. `ErrorDetail::Account` carries a secret-free summary: a refused pool selection names every candidate and what blocked it ("openai-codex:acct-b (already failed this request); openai-codex:acct-a (pinned to a different account)") and is classified as a quota or rate admission failure when only quota or rate state blocked, and as an authentication failure otherwise; a missing or unusable lease names the account and says to sign in again. A missing credential records the account as a failed pre-commit attempt and asks for `RotateAccount`, so discovery and unpinned turns move to a sibling account. The two and a half minutes were two OMP defects. The first was in the fork's kernel executor (`crates/driver/src/headless/kernel.rs`): it handed the environment the dispatcher's `blocking_limit` (30 s, "how long the turn waits before detaching the call into a job") as the invocation `deadline_ms`, which envd treats as "kill the tool at this time" (`native invocation deadline exceeded`, then the shell's `bash command was cancelled`). So every bash call longer than 30 s was detached and killed in the same instant, the abort sat in the detached call's event queue until the next `JobBoard::poll` (the model's next tool call), and the job was journaled failed with a duration equal to the gap between detach and that call. The model then retried, which is where the minutes went. Upstream `omp2` carries the same line. The first attempt replaced the constant with 300 s, which the user rightly rejected as the same defect with a longer fuse. The real fix is ownership: `InvokeTool.deadline_ms = 0` now means no environment-enforced deadline, and the kernel sends zero by default (`DispatchPolicy.execution_limit` is `None`) because it already owns each invocation's lifetime through the blocking-limit detach, job-board cancel, and session end; a tool's own timeout still applies. Inside envd the admission gate, the native run loop, and the extension-host call carry an optional deadline (`invocation_deadline`, `deadline_elapsed`, `EventDeadline::after`), while device and prelude helper calls keep explicit ones. This also stops the environment denying an approval prompt the user had not answered within the blocking limit. Tests: `worker_routed_tools_use_the_injected_external_executor` asserts the executor gets no ceiling, `a_gate_without_a_deadline_never_expires_on_its_own`, and the contract test `an_invocation_without_a_deadline_runs_until_its_client_ends_it`. Removing the deadline exposed the next layer: at 60 s the shell's own foreground threshold (`sv_shell_auto_background_threshold_ms`) detached the process into a named job and ended the invocation, which the kernel cannot use (it neither parses the `detached` verdict, "environment returned an invalid outcome artifact", nor monitors named processes), so a 90-second command still died at 60 s. A client that asks for no deadline owns the lifetime, so envd now runs the invocation inside `omp_tools::auto_background::with_client_owned_lifetime` and the shell and eval tools skip their own detach (`de19c20eee`, test `a_client_that_owns_the_lifetime_keeps_the_command_in_the_foreground`). Proof: the headless harness with a 90-second bash prompt now goes detach at 30 s, one `hub wait`, completed at 90.2 s, output read, one final answer. The second defect was the merge back: the child's task succeeded but `merge_worktree` failed with `ExternalInvalidation` on an untouched tracked file, and the wrapper marked the child failed. The fork now keeps such a child `completed` and reports the merge failure as a `warning` on the job board (`rpc_subagents`), which the row shows as "done · … · changes not merged" and the tooltip explains. Why the document server invalidated `BASELINE.md` in the first place is still open; the envd watcher also churns on `vendor/oh-my-pi/target`.

Fixing the deadline exposed two more OMP defects in the same flow, both fixed in the fork. After the job completed, the model read its settlement at the `artifact://sha256/…` address the kernel gave it and envd answered "Artifact storage I/O failed: No such file or directory": the kernel spills the settlement into the session journal's CAS, while envd's artifact resolver (`crates/envd/src/tool_url/artifact.rs`) looked only in its main blob store. The settlement is the tool's own verdict, which envd retains under `blobs/verdicts`, so the resolver now falls back to the verdict store (`55d671632d`). That read failure then ended the turn outright, because the fault's projection carried no text and Anthropic rejects an error tool result with empty content (HTTP 400, "content cannot be empty if `is_error` is true"); `commit_terminal` now describes such an error from its fault ("tool failed: …", `6131d86736`). The proof is the headless harness (`scratchpad/repro_spawn.py` with a 40-second bash prompt): before, the job settled failed at the next tool call; after the deadline fix alone, it settled completed but the artifact read failed and the turn died; the helper is built only from the fork's committed HEAD (`scripts/build-omp-helper.sh` clones it), so an uncommitted fork change never reaches a repro.

`hub` is OMP's desk for background work: the parent agent's one tool for waiting on sub-agents and detached jobs (`wait`, `jobs`, `cancel`), talking to peer agents (`send`, `inbox`, `list`), and running named processes (`start`, `stop`, `restart`, `logs`, `ps`, `describe`). ### Phase 18: A tokens-a-second speedometer and a Metrics page, 2026-09-15

The user asked for a speedometer that is true to the rate the API yielded tokens at and matches the conventional measures, metrics recorded in a parsimonious format beside the sessions, and a view of how much of a turn is spent waiting for inference against the tools the harness calls. The measurements come from the fork, where the stream is consumed: the agent loop already stamped the request start and the first streamed token for the journal's `turn.receipt` (`ttft_ms`, `duration_ms`); it now also stamps the last streamed fragment (text, reasoning, tool-call start, or tool-argument delta) as `last_token_ms`, carries the provider's reasoning subset as `tokens_reasoning`, and names the route that answered in `identity` for primary responses (consumers filter on `role == Advisor`, so a Primary identity changes nothing for them). The kernel publishes each settled receipt as `KernelEvent::InferenceReceipt`, which RPC mode sends as an `inference_receipt` frame (`provider`, `model`, `tokensIn`, `tokensOut`, `tokensReasoning`, `cacheRead`, `cacheWrite`, `costNanoUsd`, `ttftMs`, `lastTokenMs`, `durationMs`); Omperor projects it to `UiEvent::InferenceReceipt`. Throughput is output tokens (reasoning included, as every provider counts them) over the span from the first streamed token to the last, which is what the public benchmarks and provider dashboards mean by output speed; the one departure is honest rather than flattering: when a provider counts reasoning tokens but streamed no reasoning at all (Omperor saw no thinking delta for the response), that reasoning happened before the first token and is left out of the rate instead of being credited to the visible span (`Inference::reasoning_hidden`, `timed_tokens`). A response under 50 ms or two tokens has no rate rather than an absurd one.

The record lives in `src/metrics.rs` and is written to `metrics.jsonl` in OMP's sessions directory, one JSON object per line with a `k` of `inference`, `tool`, or `turn`; zero and absent fields are left out. An inference line carries the receipt plus `at` (unix ms when it settled), `session`, `turn` (the unix ms the turn started, which stays unique across relaunches), and `fast` when the request asked for the priority tier; a tool line carries `tool`, `duration_ms`, and `error`; a turn line carries `duration_ms` and `outcome`. Inference timings are OMP's; tool and turn spans are Omperor's, stamped when the runtime thread received the event (`ArrivedEvent`, `apply_omp_event(event, arrived)`, `wall_clock_ms_at`) rather than at the main thread's 30 Hz poll, which had let a turn read shorter than its own inference. `metrics::Log` appends on its own thread; `metrics::read` and `metrics::summarize` fold the file for the page. A turn's split (`TurnSplit`) is: waiting for the first token (Σ `ttft_ms`), receiving tokens (Σ `duration_ms − ttft_ms`), running tools (the union of tool spans, so parallel calls count once), and harness and everything else (wall minus the union of inference and tool spans, clamped at zero). Sub-agents run inside the `task` tool, so their inference counts as tool time; the page says so.

The speedometer sits at the chat header's right (`SpeedometerView`, a half-circle dial drawn with `NSBezierPath`; `SPEEDOMETER_WIDTH`): the needle, the rate beside it, and under that the response's time to first token and token count. While a response streams the needle follows an estimate (`metrics::LiveRate`: characters over the last two seconds divided by the characters per token the previous response of the model taught, drawn in the paler gold with a `~`); when the receipt arrives it snaps to the exact figure. The dial's scale doubles when a rate runs past 85 % of it, so a fast model is never pinned. `tick_speedometer` runs from the runtime poll at 10 Hz while streaming. Settings › Metrics (`SETTINGS_METRICS_PAGE`, `sync_settings_metrics_ui`, `metrics_page_plan`, `MetricsCardPlan`) is a list and a detail: down the left, "All sessions" and then every session the log knows, newest activity first, titled the way the sidebar titles it (`metrics::sessions`, `metrics_session_rows`, `MetricsSessionRow`; rows are two labels with a transparent button added last, so it sits on top: a label added over the button takes the click itself and the row goes dead, which the user hit; the pattern elsewhere (agent rows, the Fast chip) is the same, button last; a gold pill sits behind the chosen row; `MetricsSelection` starts `Unchosen` and settles on the open session when the log has something for it, otherwise everything; the user asked for a list rather than a dropdown so it scales), and on the right a "Where the time went" card with a stacked bar and the four shares, "Throughput by model" (responses, median and p90 tok/s, median TTFT, how many asked for Fast), and "Tools" (calls, total, median, errors), with Refresh and Reveal log. The log is read on a worker (`request_metrics_read`, `BackgroundEvent::MetricsRead`) when the page opens, and once read, records made in this process are appended to what was read (`record_metric`, `metrics_ui_dirty`) so an open page follows the turn. Verified on the real store: a limerick turn recorded `tokens_out 116`, `ttft_ms 6648`, `last_token_ms 6985` (344 tok/s, the whole answer arriving in a 337 ms burst after a 6.6 s wait, which is what the API did); a read-tool turn recorded two responses, one 59 ms `read`, and a 5.6 s turn. The redesign is that an assistant message is set by the block: `markdown::split_blocks` cuts a body at blank lines outside fences unless the next line continues a list, an indented block or an HTML block (a body still being written keeps its last block open until the next line decides), link reference definitions anywhere in the body are gathered and appended to each block's parse — kept out of an open fence, where they would read as code — and `blocks_parse_the_same_alone_as_together` holds the whole parse equal to the sum of the parts across the mock template and every streaming prefix of it (an empty paragraph no longer leaves a newline behind, the one quirk that broke it). `native_markdown::render_message_incrementally` renders a message as speaker line, blocks and spacer, reusing from the previous render every block whose source, preceding paragraph and definitions are unchanged (the block before the first changed one is given back to the split, since the cut after it was decided by the line that followed), and reports the UTF-16 length of the unchanged prefix; `refresh_chat_transcript` edits only the changed tail into the text storage, so TextKit lays out only that, and messages unchanged at the end of the transcript are no longer re-inserted behind a change in the middle. User, tool, thinking and notice messages are still set whole (the user's box needs one enclosure block). `Conversation` now tracks `Changes` — `take_changes()` hands the transcript the edited indices, or `All` after a load or prepend — so fingerprints are recomputed only for those, instead of every body being cloned and hashed thirty times a second. ### Phase 32: A timeline that streams, newest first, 2026-09-22

Opening the timeline of session `01M30XF8KTV881T8J22B2W0K3B` (2,891 events over 25 hours: 1,435 responses, 1,429 tool calls, 16 sub-agents) hung the app. The fold was already on a worker and took 58 ms; the hang was `layout_timeline_rows_now` building eight to ten `NSTextField`/`NSBox`/`NSButton` views for every event on the main thread, about 25,000 views, and building them all again on every resize, filter keystroke, and opened run. Measured on the old build: the first rows appeared after 7.9–8.7 s, inside a single 13.2–13.6 s main-thread pass, and each window resize blocked for 8.7–11 s.

The timeline now arrives the way the chat's history does. `timeline::stream` runs on its own thread (`omperor-timeline`): it folds the session and its sub-agents, sends a `timeline::Summary` (totals, span, longest, p90, models, all fixed before any row shows, so the bars' scale never moves) with the newest 48 events, then older pages of 256 until the session's start, over a `flume::bounded(1)` channel, calling `gui_wake::notify` after each. `poll_timeline_stream` (from `backgroundJobsReady:` and the tick, which stays at 30 Hz while a stream is open) takes one page per call. Dropping the receiver, which closing the window does, stops the worker at its next page. The window opens scrolled to the newest event at the bottom, and a footer spinner reads "Reading the journal…" and then "Loading earlier events · n of N" until the last page. `timeline::Loaded` holds what has arrived, indexed by each event's place in the whole session, so a row, an open sheet, and an opened run keep their meaning while older events are put in front. Opened runs are keyed by where the run ends (`Row::run_key`), which does not move when older hidden events lengthen the run at its front. The search text of each event is set once when the fold finishes (`Event::search`), not per keystroke.

The list (`src/timeline_ui.rs`) is virtualized the way a table view is. `TimelineList` owns the document, the rows, their tops (`timeline::row_tops`), and a view for each row within 160 points of the visible area (`timeline::rows_between`). Views are keyed by the `Row` itself, so a relayout keeps the views of rows that did not change. The document is not flipped, so a prepended page grows it at the top and the clip keeps showing the same rows. Each `TimelineRowView` is one view that draws its own row from text attributes built once per thread (`Styles`). AppKit asks every live row to redraw the scrolled strip on every step of a programmatic scroll: every row's view, not just the rows entering. The mismatch between flipped rows and an unflipped document, `copiesOnScroll`, the redraw policy, and explicit layers all left that unchanged, and explicit row layers made passes slower. So a row draws from its text the first two times at a size, then keeps an `NSImage` of itself, and later draws copy pixels. A jump passes a row after about two draws; a scroll draws it on every step. One tooltip covers the list: a tooltip on every row made AppKit rework the window's tooltip areas each time a row appeared. The minimap buckets marks into 2-point slots, so it draws at most one bar per slot however long the session is. Neither the minimap nor a row starts a window drag.

`--timeline-smoke <journal>` checks all of this without loading the user's sessions or starting inference, and without activating the app. An earlier version did activate it; the user's typing elsewhere landed in the timeline's search field and failed the run. The smoke opens the window, waits for the newest rows and then the whole session, scrolls a screen at a time to the oldest event, glides back 24 points a frame for 300 frames, filters by "hub" and clears, and resizes. It then prints the time to first rows, the time to the whole session, the worst pass, over-budget passes, and rows drawn and set per tick for each phase, and exits 1 on failure (every event arrived, the oldest row is in view at the top, no more than 64 row views at once). With `OMPEROR_TIMELINE_SMOKE_SHOTS=<dir>` it pauses to let `screencapture -l` take pictures of its own window. Run it with an isolated `HOME` and copies of the journals. Results on that session, release build, three runs: first rows in 159–229 ms and the whole session in 181–245 ms. Apart from app launch, the load passes are one 16 ms first paint (including the process's first text draw) and 5–7 ms pages. Gliding had 2–3 of 300 passes over budget, worst 4.1–4.3 ms apart from one 11 ms outlier. A screen-sized jump is one 4.7–5.3 ms pass (p50). A resize costs 6–8 ms. At most 21 row views existed at once. Still over budget: a screen-sized jump and the first paint. Real trackpad scrolling uses AppKit's responsive path, which the smoke cannot drive, so it may repaint less than the smoke measures.

### Live inference data flow

```text
AppKit text field / menu action
            │
            ▼
AppDelegate validates UI state and updates Conversation
            │
            ▼
flume Command channel
            │
            ▼
OmpRuntime worker thread + current-thread Tokio runtime
            │
            ▼
omp_rpc::RpcClient ── spawns release `omp rpc` child
            │
            ▼
OMP session actor ── provider inference and native tools
            │
            ▼
RPC events projected into UiEvent values
            │
            ▼
flume event channel polled by AppKit timer
            │
            ▼
Conversation mutation ── native Markdown render ── NSTextView
```

Commands include prompt, steer, abort, new session, resume session, open project, set model, set reasoning, provider login, authentication answers, and shutdown. UI events include connection/readiness state, model/account state, text and thinking deltas, tool lifecycle events, authentication events, failures, and final turn results.

The AppKit main thread never waits synchronously for OMP startup or inference. The background runtime owns the RPC client and relaunch loop. The UI currently polls delivery at approximately 30 Hz, which measured around 34 ms p95 event-to-GUI latency; replacing polling with an event-driven main-thread wakeup is a reasonable future polish item but not a current correctness problem.

### Child lifecycle and recovery

The OMP executable is resolved in this order: `OMPEROR_OMP_EXECUTABLE`, the app bundle's `Contents/Helpers/omp`, then the development release binary. Debug Omperor bundles contain a tiny launcher that points to the stable release helper, while release bundles copy the release helper into the app.

The app icon lives at `assets/01-crowned-gate.svg` (the sidebar's crown on the macOS icon square; the `-light` and `-mono` files beside it are earlier gate designs nothing references). `scripts/build-app-icon.sh` rasterizes it into the committed `macos/AppIcon.icns` through `scripts/render-app-icon.swift`, which draws the SVG with AppKit's own renderer at every iconset size, before `iconutil` packs the sizes; the artwork fills the canvas and the system masks and shadows it (Phase 31). `build-app.sh` only copies the committed icns into `Contents/Resources`, and `Info.plist` names it through `CFBundleIconFile`/`CFBundleIconName`, so an app build never depends on the icon tooling. Re-run the icon script (`just icon`) and commit the refreshed icns after editing the SVG.

Startup waits are bounded and continue processing control commands, so quit, project switches, new sessions, and recovery requests cannot become trapped behind a spawn future. When a child disconnects, the runtime reports the failure, applies a recovery action where appropriate, and relaunches with the current project/model/session configuration. Shutdown sends the graceful RPC path, waits asynchronously, and only allows `NSApplication` termination after the worker has been reaped; the lifecycle test also verifies that helper PIDs do not survive the parent.

The user specifically expects functional lifecycle tests to send an actual message, not merely launch and quit the window. Any new RPC reliability change should therefore include a real prompt/response check in addition to process-lifetime assertions.

## Session ownership and persistence

Omperor deliberately separates its writable state from normal OMP/TUI state:

| Data | Default path | Ownership |
|---|---|---|
| Preferences SQLite | `~/Library/Application Support/Omperor/omperor.sqlite3` | Omperor |
| Writable Omperor sessions | `~/Library/Application Support/Omperor/omp/sessions` | Omperor and its managed OMP child |
| Omperor OMP data/credentials | `~/Library/Application Support/Omperor/omp/data` | Managed OMP child |
| Development state | `~/Library/Application Support/Omperor Dev` with the same layout as production | Omperor Dev and headless evals |
| Legacy/external sessions | `~/.omp/agent`, `~/.local/share/omp`, or external `OMP_DATA_DIR` roots | OMP/TUI; read-only in Omperor |

The SQLite database is in WAL mode with a three-second busy timeout and carries `PRAGMA user_version = 1`. The unconditional `preferences(key, value)` table stores active project, model, reasoning level, appearance, transcript size, and inline-image preference. Migration 1 adds `accounts`, keyed by OMP's `account_id`, holding the user label, last known principal, the time the account was first seen or authenticated through Omperor, and the per-provider default flag, plus `project_accounts`, keyed by workspace path and provider, holding the account last used there. New schema changes must add a step to `migrate` in `src/preferences.rs` and bump `SCHEMA_VERSION`. Rows in `accounts` are pruned only against a complete, successfully fetched OMP account list so a transient listing failure cannot erase labels. Diesel and `diesel_async` were intentionally not introduced; the current synchronous `rusqlite` operations are tiny local transactions, and SQLite's single-writer nature means an async ORM would not add useful concurrency at this stage.

Session discovery emits app-owned results first and external results second. The sidebar defaults to the Omperor source and labels the external source `OMP · Read-only`. Omperor-owned sessions are resumed through a newly launched managed child using the session ID and original project. If the requested session cannot be resumed exactly, the UI falls back to read-only rather than risking writes to the wrong session.

History paging reads JSONL backward in 64 KiB chunks, renders an initial tail of eight messages, then sends older pages of sixteen messages. The transcript restores a character/geometry viewport anchor after each prepend so background history does not cause visual jumps. Both current chronological records and older branch/chain-style sessions are supported.

## Native Markdown and transcript rendering

The renderer is intentionally two-stage. `pulldown-cmark` parses GFM into a framework-neutral `MarkdownDocument` whose ranges are tracked in UTF-16 units, then `native_markdown.rs` maps those ranges to AppKit attributed-string APIs. This avoids parsing Markdown directly into ad hoc visual mutations and makes the parser independently testable.

Text uses native system and monospaced system fonts. Code blocks use a fixed baseline grid with zero per-line paragraph spacing, native TextKit block padding/borders, and OneHalf light/dark syntax themes from `two-face`/`syntect`. Markdown tables use `NSTextTable`; images use `NSTextAttachment` and load through two background workers with a 10 MiB limit and a 15-second HTTP timeout. Unsafe or unsupported link schemes are not activated.

Transcript messages are fingerprinted and cached as attributed strings, so unchanged messages are not rerendered on every streaming update. The initial cold Markdown render was measured near 31 ms, while subsequent renders were generally below 0.8 ms. When the user scrolls away from the bottom, streamed content no longer steals the viewport; when the user remains near the bottom, new output continues to follow automatically.

Tool activity renders as a single self-contained line with no speaker prefix: a status glyph (`✓` green completed, `✗` red failed, `●` yellow running), a past-tense description of what the call did, and a trailing `›` chevron. `chat::describe_tool` maps the tool name to a verb and pulls its most identifying argument as the object — `Read <path>`, `Ran <command>`, `Listed <glob>`, `Searched <pattern>`, `Wrote <path>`, `Edited <file>` — so the row says what happened rather than naming the tool. The whole row carries a `omperor-detail:<id>` link that the transcript's `NSTextViewDelegate` intercepts to open the full arguments, updates, and result in an `NSAlert` modal; the transcript's `linkTextAttributes` strips AppKit's blue underline and keeps only a pointing-hand cursor, and omits a foreground colour so each run keeps the colour it was rendered in. Reasoning renders as quiet italic prose with the same chevron.

Both paths draw a tool row through one shared `chat::tool_row` (summary plus detail body from the name, arguments, updates, result, and intent), so the live and reopened transcripts read identically. Their inputs arrive differently, though. In RPC mode OMP never streams `toolcall_delta`, so the live path must take the full arguments and intent from the `tool_execution_start`/`_update` events' `args`/`intent` fields (`omp_runtime` projects them; `Conversation::set_tool_context` records them) — dropping those, as an earlier version did, is what left live rows as bare verbs while a reopened copy of the same session read fully.

Reopened sessions read from the journal instead. `journal.rs` folds each `.oms` tool call across the several entries that describe it — the `tool.call` names the tool, an optional `kernel: ready` `tool.update` carries streamed arguments, and the `tool.result` (linked by its causing entry id) settles success or failure and supplies the model-facing text — into an enriched `SessionMessage` that reuses `chat::describe_tool` and `chat::tool_detail`, so the summary, status, and detail modal match the live transcript. `think` calls fold into reasoning rows rather than tool rows.

A failed tool call is not a turn failure. The model routinely retries a bad call and recovers, so a completed turn adds no summary line — the failed step already carries a red status glyph, and that is the whole signal. Only when OMP reports the turn itself ended abnormally does a `turn` note appear: `omp_runtime` reads `agent_end` into a `TurnOutcome` (`Errored(reason)` from its `error`, `Interrupted` from `cancelled`, else `Completed`), and `Conversation::note_turn_end` surfaces OMP's reason for an error or an interruption. This matters because RPC mode drops the turn error otherwise — nothing else reports it.

The detail modal presents that payload as a styled document, not a monospaced dump. `tool_detail` builds the body as `Intent`/`Arguments`/`Updates`/`Result` sections joined by blank lines; `Conversation::detail` re-splits the stored body back into `DetailSection`s (a chunk that does not open with a known heading continues the section before it, so a blank line inside a result does not start a spurious section, and reasoning stays one unlabeled prose block); and `native_markdown::render_detail` renders each — quiet uppercase letter-spaced headings, prose for the intent, and monospaced, JSON-syntax-highlighted payloads for the code sections, reusing the transcript's `apply_highlighted_line` and theme.

The user has unusually high standards for typography and code composition and has explicitly asked that visual correctness be inspected, not assumed. For renderer changes, build and launch the actual app, exercise representative Markdown with a real agent turn or the snapshot example, capture the UI after granting Screen Recording access, and inspect line height, paragraph rhythm, wrapping, table geometry, code alignment, colors, and scrolling behavior.

## GUI iteration and desktop-control praxis

GUI work is not complete when Rust compiles or an accessibility query finds the expected label. The established loop combines programmatic desktop control, accessibility-state assertions, full-resolution screenshots, direct visual inspection, real OMP inference, and process cleanup. Preserve all of these layers because each catches a different class of failure.

### 1. Establish a clean launch target

Before rebuilding, check whether that edition is running. Omperor and Omperor Dev may run together after both have the state-isolation helper patch. Do not kill unrelated `omp` TUI processes: Omperor’s child must be identified through the Omperor PID or its exact helper path. Do not replace a bundle while its sessions are running.

For ordinary iteration, build a debug Omperor shell with the stable release OMP helper, then launch a new app instance:

```bash
APP_PATH="$(scripts/build-app.sh --debug)"
open -n "$APP_PATH"
APP_PID="$(pgrep -n -x omperor)"
```

Use `scripts/run-app.sh` for the normal one-command path. Avoid `--rebuild-omp` unless an OMP source, patch, embedded-Python, linker, toolchain, or build-flag input actually changed; a forced helper rebuild is slow and can turn the next OMP launch cold.

### 2. Drive controls semantically

Use macOS Accessibility through `System Events` or the available desktop-control facility to locate controls by role, title, placeholder, or accessibility attribute. Prefer semantic lookup over fixed screen coordinates so the automation survives window resizing and layout changes. The existing lifecycle/profiling scripts demonstrate the working pattern: select the application process by Unix PID, make it frontmost, locate the control, set or click it, and poll visible accessibility text for the expected state.

```bash
osascript \
    -e 'tell application "System Events"' \
    -e "set appProcess to first application process whose unix id is $APP_PID" \
    -e 'set frontmost of appProcess to true' \
    -e 'click button "New chat" of splitter group 1 of front window of appProcess' \
    -e 'end tell'
```

For prompt entry, locate the text field whose `AXPlaceholderValue` is `Message OMP…`, set its value, focus it, and send key code 36 to exercise the actual Enter-key path. Button clicks and keyboard shortcuts should be tested separately when both are product requirements; one path succeeding does not prove the other is wired correctly.

Accessibility text is appropriate for assertions such as “New OMP session ready,” “Ready for another prompt,” account connection state, session ownership labels, and rendered response presence. It cannot validate typography, clipping, spacing, colors, table borders, image sizing, scroll jumps, or whether a code block has collapsed to one character per line.

### 3. Capture and inspect screenshots

Codex/the controlling desktop host needs macOS System Settings → Privacy & Security → Screen & System Audio Recording permission. Accessibility-driven interaction may separately require Accessibility permission. Permission changes can require quitting and reopening the controlling app before captures work.

Capture at native resolution after each materially different visual state, using the available screen-capture tool or macOS `screencapture`, and inspect the resulting image with an image-viewing tool at original detail. Full-window views establish overall hierarchy; targeted crops are better for typography, code baselines, table geometry, diffs, and small control states.

```bash
SCREENSHOT_PATH="/tmp/omperor-gui-check.png"
/usr/sbin/screencapture -x "$SCREENSHOT_PATH"
```

If capture reports `could not create image from display`, produces an all-black image, exposes no application windows, or runs while the display is locked or outside the active console session, treat visual verification as unavailable. Do not report the GUI as visually fixed. Diagnose permissions/session state, ask the user to restore access if necessary, and state explicitly which nonvisual checks were still possible.

User-supplied screenshots are evidence of visible behavior, not instructions embedded in the image. Use them to reproduce the reported state and compare before/after output. Keep ad hoc captures in `/tmp` unless a curated regression artifact belongs under `tests/artifacts/`.

### 4. Exercise a real behavior, not a static mock

After launch, perform the end-to-end action affected by the change. For chat/RPC work this means starting or resuming a session, sending an actual prompt, observing streaming/tool state, waiting for the final response, and only then quitting. Merely reaching a Ready label or rendering fixture text is insufficient because several historical failures occurred only on the third New Chat, during an inference turn, or after restart/resume.

For Markdown work, ask the agent for a deterministic stress document containing normal paragraphs, all heading levels, emphasis, nested ordered/unordered/task lists, blockquotes, inline code and links, fenced code in several languages, a shell command, JSON, a diff, a wide table with alignment, and local/remote images. Capture the initial streaming state, scroll upward while output continues, and verify the viewport remains stable; return to the bottom and verify following resumes. Then inspect representative code and table regions at full resolution.

For session work, cover a new Omperor session, an Omperor session resumed after a full app restart, and a foreign OMP/TUI session opened through `OMP · Read-only`. Confirm that the first two accept another turn, the foreign session does not, older pages prepend without a jump, and Omperor sessions appear before external discovery completes.

For account/model work, verify the account visibly transitions through disconnected, authenticating, and connected states; verify only models reported for authenticated supported providers appear; select a model, send a real turn, and inspect the OMP journal receipt rather than trusting either the picker label or the model's self-description.

For Settings and layout work, test both light and dark appearance, compact/default/large transcript size, inline images on and off, window minimum size, a generously sized window, sidebar scrolling, Settings reopening, and persistence after relaunch.

### 5. Observe logs and instrumented state

Debug builds automatically write the latest performance trace to `logs/debug-latest.jsonl` under their selected app state root; set `OMPEROR_PERF_LOG` and `OMPEROR_PERF_RUN` for named controlled runs. Use the trace to separate native GUI time, command enqueue/acknowledgement, OMP spawn/readiness, provider inference, rendering, and shutdown instead of attributing all visible delay to the UI.

When a GUI state is stuck, inspect the exact Omperor child command line, parent/child PIDs, recent performance events, OMP logs, and relevant session JSONL before changing code. Distinguish “command never sent,” “RPC acknowledgement missing,” “provider turn stalled,” “event arrived but GUI did not consume it,” and “GUI state updated but rendered incorrectly.” These have produced superficially similar screenshots but require different fixes.

### 6. Close cleanly and prove cleanup

Quit through the real application path with Command-Q or the application menu so `applicationShouldTerminate` and graceful RPC teardown execute. Wait for Omperor to exit, then verify only the helper children that belonged to that Omperor PID are gone. Do not use a broad `pkill omp`, because a user may have unrelated TUI sessions running.

Run `scripts/test-app-lifecycle.sh` after lifecycle changes to cover early-startup quit races and a ready RPC child. Run `scripts/profile-omp-lifecycle.sh` when the change touches readiness, inference latency, event delivery, or shutdown; it drives a real `pong` turn rather than measuring launch alone.

### 7. Report verification precisely

In the hand-off for a GUI change, state which build was tested, which control path was exercised, whether a real inference occurred, which screenshots were inspected, which appearance/window states were covered, whether session restart/resume was included, and whether child cleanup was verified. Separate compilation/unit-test success, accessibility assertions, functional end-to-end success, and visual inspection; never collapse them into an unqualified “fixed.”

## Settings and account/model behavior

The Settings window is native AppKit and currently contains:

- General: active workspace and a folder chooser.
- Agent: dynamically discovered default model, reasoning effort, a description of the standard tool set, and a "Refresh Models…" action that re-runs account model discovery and relaunches the child on the same session.
- Appearance: system/light/dark mode, compact/default/large chat text, and inline-image visibility.
- Sessions & Data: the Omperor session and backend-data paths with Finder reveal actions.
- Projects: one card per project with its recorded session count, each folder with a Remove button (missing folders shown in red), and Rename, Add Folder, and Delete Project actions; General shows the active project and links here.
- Accounts: one card per provider listing every stored account with its label or identity, a Default radio, Label/Rename and Remove buttons, a connection summary, and an Add/Connect action; the card body scrolls when accounts outgrow the page.

Account identity shown to the user is the subscriber email when OMP reports one as the principal (Anthropic) and otherwise the authentication time (OpenAI Codex reports a workspace UUID; the email exists only in its ID token's profile claim, which OMP does not surface during listing). The composer's account control is a transparent popup like the model and reasoning pickers; it lists the active provider's usable accounts, shows "choose account" when nothing is pinned, and switches the live session through `set_account`, after which the workspace choice is stored. Switching to a model of another provider resolves that provider's account first and launches the fresh session with the pin already in the launch configuration, so recovery, New Chat, and resume re-pin before Ready.

Only models belonging to authenticated supported subscription providers appear. OMP is the source of truth for availability; Omperor should not invent, scrape, or hard-code future Anthropic model names. Switching provider families creates a fresh session where required. Picker state should change only after OMP confirms the selected model, because optimistic labels previously concealed failed model changes.

When a provider returns an authentication failure, Omperor removes it from the in-memory authenticated set, disables sending for its models, changes the account state to Connect, and prompts the user to authenticate again. Advanced account-security changes were one real trigger for this path.

## Projects, directories, and worktrees

The Environment pane's Git inspector re-inspects the active directory whenever a tool that can change files finishes (anything except the read-only set in `tool_may_change_files`: read, grep, glob, think, debug, todo, ask, web_search, recall, reflect, goal, report_issue) and again when the turn ends. Requests coalesce: an inspection already in flight records one pending refresh and runs it on completion, so a turn with many edits costs at most two `git status` runs. The file the user is inspecting stays selected across refreshes and its diff reloads; a file that disappears is reported as no longer listed, and previewing a path removed after the last inspection triggers a fresh inspection instead of a raw read error.

The pane itself (`build_inspector`, `INSPECTOR_WIDTH` 336) is laid out as a status panel rather than a form: under the title and a status line carrying the project path, three summary rows built by `inspector_row` — a symbol, a quiet label, and a right-aligned value — for the branch, the upstream (`Up to date`, `↑n to push  ↓n to pull`, or `No upstream`, from `git rev-list --left-right --count @{upstream}...HEAD`), and the last commit's subject (`git log -1 --format=%s`); a hairline; then a `CHANGES · n` section label with the tree's total `+added −removed` on its right, a scrollable list of one row per change (`change_row_button`: a colored monospaced badge — A green, M orange, D red, R blue, U red — then the directory in secondary and the file name in label color, with the file's own counts in a right-aligned label beside it), and below that the selected file's diff under a title line (`set_diff_title`: path, kind, counts). Line counts come from `git diff --numstat -z HEAD` (`parse_numstat` handles binaries as `-` and renames as an empty path followed by the old and new paths) and, for untracked files, from counting the file's own lines (`untracked_line_count`; a directory or binary has none); `WorkspaceSnapshot::totals` sums them. Rows are plain `NSButton`s tagged with their index and wired to `selectChange:`; `highlight_change_row` places a gold pill behind the selected one, `populate_change_list` rebuilds the rows and splits the space — the list takes what its rows need up to two fifths of the pane, the diff takes the rest — and `restore_selected_change` re-highlights by path after a refresh. The diff's text view does not wrap (`horizontallyResizable`, a huge container, a horizontal scroller), since a folded diff loses the alignment it is read by. The old `NSPopUpButton` file chooser is gone.

A project is a durable record with a stable id, a display name, an ordered list of folders, a collapsed flag, and a last-opened time. Each session is bound to exactly one directory: one of its project's folders, or a worktree Omperor created for a fork. The delegate's `current_project` ivar still holds the directory the running child works in (its name predates projects), and `active_project_id` names the project that owns it. The directory determines the OMP child working directory, the directory exposed to agent tools, the Git repository inspected by the environment sidebar, the base for relative Markdown images, and the per-directory state OMP keeps under its data directory. Changing directory relaunches the child; starting a chat in the same directory reuses it.

Membership is resolved at display time. A session with a row in `sessions` belongs to that row's project; otherwise its `cwd` is matched against every project folder and every recorded session directory or worktree path; otherwise it is shown under "Other folders". Foreign read-only OMP sessions never join a project. Account choices are keyed by project id, so every folder of a project shares one chosen account per provider.

Forking is how work splits: any Omperor session can be forked into a fresh session seeded with its transcript, in the same folder by default because two sessions can work on orthogonal parts of one checkout. When deconfliction is wanted, "Fork into New Worktree…" creates a branch and worktree from the commit the folder has checked out and runs the fork there. Forks can fork again; lineage is recorded and shown in tooltips, not as sidebar nesting. Omperor never deletes a branch. Deleting a project only unfiles its sessions; deleting a session removes the worktree Omperor created for it only when no other session uses it and git finds it clean (see below).

The direction these decisions must stay compatible with is agent teams and swarms made legible in the GUI: first many sessions on one repository, each on its own branch and worktree, later work-graph tools in the style of Doodlestein's beads and beads-bv. What still needs design before that:

1. A runtime pool keyed by session so several children run at once; the data model already allows it, only `OmpRuntime` assumes one child.
2. Moving a session between projects and re-parenting forks, which today are metadata edits without UI.
3. Worktree lifecycle: showing merged or stale branches. (A deleted session's clean worktree is removed; see below.)
4. Surfacing the fork tree and branch state in the environment pane, and merging or opening a pull request from a fork.
5. Which per-project defaults (model, reasoning) belong on the project record versus the app preference.

## Deleting sessions, archiving projects, and Omperor's own tools (2026-10-01)

**Deleting a session** (session menu › Delete Session…, or Discard Draft; a sheet confirms, except for a draft with nothing in it) runs `housekeeping::delete` on the job pool. It removes, beside the journal in `omp/sessions`: `<id>.oms`, `.heights`, `.heights.tmp`, the `<id>/` `local://` folder, any `<id>.rpc.json`/`.jsonl` from an older OMP, and the `.oms.lock` last. Sub-agent journals go only when no surviving journal names them: `housekeeping::graph` reads every journal's `jobs.insert` patches on every branch (fail-closed: one unreadable journal keeps all children), and `exclusive_descendants` prunes until nothing outside the deleted set refers to what remains. Each journal is held with its writer lock (`lease`, `File::try_lock`) while it is removed, so one open in any OMP process is reported and left. The registry rows (`sessions`, `session_positions`) and the session's `metrics.jsonl` lines go too; the metrics log is rewritten by its own writer thread (`metrics::Editor`), so an edit never races an append. A worktree goes only if it is under Omperor's `worktrees/` directory, no other record, listed session, or live entry uses it, and `git status --porcelain --untracked-files=all` is empty; `git worktree remove` (never `--force`) runs from the main repository, ignored files go with it, and the branch is always kept (`workspace::remove_clean_worktree`). Pasted attachments in `omp/data/attachments` are not linked to any journal and are left. Blobs are left for `omp gc`.

A live session is released first: `housekeeping_ui::start_removal` asks each idle owner to `release_session`, waits for `SessionReleased` (or `Stopped`), and runs the worker then; after 20 s it runs anyway and the lock check refuses whatever is still held. A busy session (turn, sub-agents, starting, account change, fork) is refused with the reason. On completion the interface forgets the rows, records, positions, saved views, metrics records, and live entries (`LiveSessions::remove`); the open session is replaced by a fresh draft first. `removed_session_ids` keeps a discovery pass that read the disk earlier from listing them again.

**Archiving a project** (project heading's right-click menu, or Settings › Projects › Archive…) takes exactly the sessions the sidebar lists under it (`session_project_position`, shared with `sidebar_rows_for`), drafts included. `archive::archive` holds every journal's lock, copies the blobs they refer to into a staging store (`omp_journal::gc::copy_journal_blobs`), and writes `archives/<slug>-<UTC stamp>.tar.zst` (zstd level 12): `manifest.json` first (project rows from `preferences::project_rows_in`, each session's saved view and draft key, worktrees left on disk), `metrics.jsonl`, `sessions/…`, `blobs/…`. The tarball is decompressed and every entry's size checked before anything is removed; only then do the journals (and sub-agent journals no outside session names) leave `omp/sessions` and the rows leave the registry (`remove_project_rows_in`, which also moves the remembered active folder off the project so the next launch does not file a new project for it). A `<id>.json` sidecar holds the manifest for listing. `archives/` is `0700`, its files `0600`. Folders, worktrees, and code are never touched.

**Settings › Archives** lists archives (worker `archive::list`, sidecars or the tarball's first entry) with Restore, Show in Finder, and Delete…. Restoring refuses, changing nothing, if the project or any of its session files is back; otherwise blobs are copied in, files moved back, rows reinserted (a folder another project took since stays with it and is reported), metrics restored, views and drafts reinstated, and the archive removed. Workers return the registry they leave (`preferences::load_registry`) so the main thread never reads SQLite for these flows.

**Empty sessions.** OMP writes a journal as soon as a child starts, so every chat opened and never sent leaves one; discovery does not list a journal without a conversation, so nothing could reach them (on 2026-10-01 they were 189 of 335). Settings › Sessions & Data › Remove Empty Sessions (`housekeeping::sweep_empty`) removes those no live entry, lock, or other journal claims. Empty drafts are also no longer kept: one that is not open is dropped when another session is opened and at launch (`discard_empty_drafts`).

**Omperor's own tools.** `omperor_tools.rs` is the catalog of host tools the app answers itself: `omperor_list_projects`, `omperor_list_sessions`, `omperor_delete_sessions`, `omperor_archive_project`, `omperor_list_archives`, `omperor_restore_archive`, `omperor_delete_archive`, `omperor_remove_empty_sessions`. Names are a prefix namespace because providers allow only `[A-Za-z0-9_-]`. They are never in a session by default and never in `--tools` (launch validation would kill the child): `/omperor [request]` registers them with OMP's `set_host_tools` for that session (sticky, one prompt-cache miss; re-registered on every child launched for the session via `LaunchConfiguration::omperor_tools`) and sends the request, if any, as the prompt; `/omperor off` withdraws them. A call arrives as `UiEvent::HostToolCall`; the app answers through `OmpRuntime::answer_host_tool`, which completes the waiting call directly (`HostCalls`) rather than queueing behind commands. Deleting, archiving, and deleting an archive raise a sheet naming the requesting session, the agent's reason, and what goes; a stopped turn withdraws its sheet (`UiEvent::HostToolCancelled`). The current session and busy sessions are refused in the answer. Sub-agents never get these tools (their registries are composed fresh). New tools go in the catalog (definition, `parse`, answer shape) and in `handle_omperor_tool_call`; give them past-tense lines in `chat::describe_omperor`.

The mock backend plays the tools against the app's real answers: with `/omperor` on, a prompt saying "tidy" (or `/mock scenario=omperor`) lists sessions and asks to delete the mock sessions and drafts. `--housekeeping-smoke` drives the whole feature headless in a scratch home (it refuses a home without `.omperor-housekeeping-smoke-home` beside `omperor.sqlite3`, never activates, keeps its window off every display): the agent cleanup with its sheet, Delete Session… from the session menu, Archive Project… from the project menu, Restore from the Archives page, and Remove Empty Sessions.

| Whole GUI shutdown | Approximately 22–32 ms |
| OMP-to-GUI event delivery | Approximately 34 ms p95 due to 30 Hz polling |

The key conclusion is that native GUI code is not the startup bottleneck. Cold OMP executable loading, validation, embedded runtime initialization, discovery, and environment setup dominate. Preserve the stable release-helper cache and do not tie the helper build profile to Omperor's profile.

## Known limitations and next-agent cautions

- Projects are first-class records, but one OMP child still runs at a time; opening a session in another directory relaunches it.
- `AGENTS.md` at the repository root states the one rule that came out of the fork work: never block the main thread on non-trivial compute, I/O (including OMP RPC), or shell commands. Git probes and `git worktree add` run on the `src/jobs.rs` pool and the header shows a spinner with the job's description while they run; new background work must follow the same shape.
- OMP remains a large child executable with nontrivial cold-start cost; the stable helper mitigates this but does not make the underlying binary small.
- The event bridge is timer-polled rather than directly waking the AppKit run loop.
- External OMP/TUI sessions cannot be continued or forked in the GUI; they are intentionally read-only. Since the rebase this also covers Omperor's own pre-journal `.jsonl` transcripts: the bundled OMP only resumes `.oms` journals, so those older sessions appear under the read-only OMP tab.
- Account route eligibility is persisted per account at login and re-derived from the catalog at startup by the fork's `rebind_routes`; if a future upstream drops that call, a regenerated catalog will again make every account `RouteIneligible`; since `248847efb8` the error at least names each candidate as "not enabled for this route".
- The `.oms` reader folds only user text, assistant text streams, and tool-call names; thinking, attachments, and custom messages are not rendered in history yet.
- Omperor-owned sessions can be resumed, but failed exact resume must continue to fall back safely instead of opening a different writable session.
- The app is ad-hoc signed for local development and has no release distribution, notarization, updater, or migration policy yet.
- `src/main.rs` is a large controller/view monolith and should be decomposed carefully before feature volume makes changes riskier.
- Provider model discovery is upstream data, not UI copy; preserve wire IDs exactly after stripping only known selector annotations.
- The OMP fork and the two staged patches are separate modification layers; inspect both when behavior differs from upstream.
- Do not test lifecycle changes only by opening and closing the app. Send a real message, wait for the response, then quit and confirm the child is gone.
- Preserve viewport position when prepending history or streaming content while the user is reading above the bottom.
- Preserve the all-native rendering constraint: no browser engine, no arbitrary HTML rendering dependency, and no replacement of AppKit typography with a custom rasterizer without a compelling measured reason.
- Keep prose paragraphs in this document on single source lines if updating it; that is an explicit repository-documentation preference for this hand-off.
- Account model discovery is provider-wide: OMP probes each provider's endpoint through whichever account its route selector picks (the pinned account when one is set), caches the rows in `models.db` for 24 hours, and the RPC child composes its catalog once at launch. A model that only one of two accounts can use therefore shows up for both until the next refresh, and "Refresh Models…" always relaunches the child; a session that has not persisted a transcript yet is replaced by a fresh one rather than resumed.
- The two-accounts-per-provider flows were exercised only by unit tests and code review, not visually; stage a second account by hand or sign in with a real second subscription and walk through the label prompt, composer popup, choose-account modal, default radio, and removal before relying on them.
- The label prompt, choose-account modal, rename, and remove confirmation are app-modal `NSAlert` loops. The runtime poll timer keeps firing inside them, which is intended so a login restart completes behind the prompt, but any new modal must take the `account_prompt_guard` so a nested event cannot stack a second prompt.
- Automatic account rotation and pooling remain deliberately off. OMP's pool still ranks by quota when no pin is present, and an Anthropic 429 is a same-route backoff rather than a rotation; do not describe the app as failing over between subscriptions. The one rotation the fork does perform is away from an account whose stored credential is missing (a logged-out ghost), and only for unpinned calls such as model discovery; a pinned turn on such an account reports "no credential is stored for … ; sign in again".
- `screencapture` reported `could not create image from display` for this host and System Events accessibility calls timed out; window captures and clicks were driven through the desktop-control MCP's background app tools after granting access to `com.bitemyapp.omperor`, which cannot open menu-presenting popups without full-screen control.

## Recommended immediate continuation

1. Consider keying the discovery cache by account rather than by provider once several accounts per provider are common, so the model list can differ per pinned account without a relaunch.
2. Send a real turn inside a forked worktree session and confirm the agent edits land on the fork's branch, not the parent's.
3. Add behavioral tests for project switching, app restart, session resume, and authentication/model restoration.
4. Design the session-keyed runtime pool before adding any feature that needs two children at once.
5. Give worktrees a lifecycle: list them in the environment pane and offer removal when a fork is deleted.
